# THE ASSERTIONS THIS SUITE IS PERMITTED NOT TO MAKE, AND WHY EACH ONE CANNOT CARRY A BOUND.
#
# Read by `tools/harness_verdict.sh` on a full sweep. Columns, TAB-separated:
#
#     <id>	<layer>	<always|env>	<why no bound can responsibly be set>
#
# `id` is what `_stand_down()` prints in brackets. `always` means the layer may not run without standing
# this down; `env` means it is permitted but conditional on the machine or the run.
#
# WHY THIS FILE EXISTS. A full sweep with a display cannot reach exit 0 and never will, because these
# stand-downs are structural. That makes "the full sweep is green" an unreachable gate, and an unreachable
# gate is met by deleting an honest stand-down or inventing a bound nobody earned. The reachable, checkable
# target is: EXIT 4, WITH EXACTLY THESE AND NO OTHERS.
#
#   an id appears that is not listed here          RED. Nobody quietly stops asserting something.
#   an `always` id is absent and its layer RAN     RED. The list must be tightened when a debt is paid.
#   a registered layer did not run at all          EXEMPT, and NAMED in the verdict.
#
# THE THIRD RULE IS THE ONE THAT COST TWO REWRITES. The first registry keyed on (layer, count) and would
# have failed CI's headless job with a diagnosis that was wrong: three of these layers need a display, so
# headless they whole-layer SKIP, and `${_got:-0}` scored "never ran" as "ran and stood down zero". The gate
# would have reported a debt paid and recommended tightening the list -- which would have deleted three
# real entries. A missing measurement read as a measured zero: the same root as every other finding on this
# branch, this time surfacing as a loud wrong red rather than a quiet green, which is luckier and not
# better. Found in the job matrix; confirmed here by running the sweep headless.
#
# AND THE COUNT KEY COULD NOT HAVE WORKED ANYWAY. It cannot tell "an assertion is now being made" from "a
# different machine took a different branch" -- `check_frametime` returns early on an unset SF_PERF_HOST,
# making its second site unreachable, so both present as 2 -> 1. Ids make the environment change legible:
# the set membership moves, and each member says what it is.
#
# EVERY POSSIBLE STAND-DOWN IS LISTED, not only the ones seen firing, so that this file is the complete
# list of assertions this suite may decline to make. Ones marked `env` have conditions that did not hold on
# the runs it was written from; they are permitted, not verified.
#
# AND `env` NO LONGER MEANS "UNCHECKED", which it did for the whole first life of this file. A row could
# only ever be observed FIRING, so absence meant nothing, so an `env` row could not fail in either
# direction -- six of these twelve were documentation with a tab in it, inside the file built to stop
# assertions going missing. Every row is now RESOLVED on every run of its layer, into one of three states:
#
#   SKIP:      [id]   the assertion was available and DECLINED       -- a design decision is owed
#   HELD:      [id]   the assertion was MADE this run                -- the debt is paid here; tighten
#   UNREACHED: [id]   control flow never arrived at the site         -- intact, this box cannot exercise it
#
# The first two are printed by `_stand_down()` and `_asserted()` in `tools/check_base.gd`. THE THIRD IS
# DERIVED BY THE GATE, from this file and the layer's log, and that placement is the whole trick: a branch
# that is not taken cannot announce that it was not taken, so a third state emitted at the site would be
# absence again wearing a new label. `_not_reached()` exists only to let a branch that DOES run attach a
# reason for a sibling it knows will not be entered.
#
#   registered, its layer ran, and NOTHING resolved it    RED. Nobody knows what that branch did.
#   resolved in code but no row here                      RED, in all three states, not just SKIP.
#
# WHAT THIS RETIRES. `iff:` was the previous attempt and it only reaches conditions the GATE can see in
# summary.txt -- fine for `no-display` and `perf-host`, impossible for a condition only the layer knows,
# which is most of them. The `iff:` rows are kept because they assert something accounting cannot: WHICH
# state is required GIVEN the condition. Accounting says every row spoke; `iff:` says what it must have
# said. Neither subsumes the other.

frametime.absolute-budget	check_frametime	iff:perf-host-unset	The frame SLO asserts only when SF_PERF_HOST names the machine, and it is set nowhere. A frame-timing claim on arbitrary hardware is a statement about the box. `env` because setting SF_PERF_HOST makes this one vanish. WHAT IT NOW ASSERTS, since 2026-08-22: not `p95 <= 8.33ms`. That comparison was the project's only 120fps assertion and it was invalid on the one kind of display it could run on -- under vsync a frame lands on 1.0x or 2.0x the refresh and nothing between, so p95 measures the pacing rather than the work. Turned on for the first time it failed all four phases including RUN at p95 9.46ms with 0.0% of frames missing their slot: a phase comfortably holding 120fps, marked as under it. It is replaced by a two-term SLO -- the share of frames past 1.5x the interval, and how late the worst one is -- both ratcheted onto five measured runs with margin, and both shown to fail under a mutant that tightens them below the measurement. The row stays because the SLO is still a claim about ONE named box and nothing sets SF_PERF_HOST in CI.
frametime.paced-phase	check_frametime	env	The paced-phase question, ANSWERED AND THE ROW KEPT, in the way save-durability.failed-backup is kept. It existed because a vsync-paced p95 inside the budget cannot tell a fast phase from a pinned one, so the reading was reported and not banked. The 2026-08-22 SLO removes the confound rather than working around it: pacing cannot fake a deadline-miss RATE or a worst-frame SEVERITY in either direction, because a frame that fits presents at 1.0x and one that misses at 2.0x, so both terms read the same number whether the panel is waiting or the game is. There is no paced branch in the assertion any more and this row now resolves ASSERTED on any run that has an interval. It still fires for the one case that genuinely cannot be measured: a display that reports no refresh rate at all, against which neither term is even defined.
grapple.gr05-preview-share	check_grapple_reads	always	GR-05's share of the throw the preview inks. The cap that stood here was 1.01 over a quantity `_corridor_fill` bounds at 1.0 BY CONSTRUCTION -- an assertion that could not fail. Removing it was right; what is owed is a design call, not a guessed bound.
grapple.gr03-single-frame-bow	check_grapple_reads	env	GR-03's single-frame bow. RESOLVED, AND THE ROW IS NOW A GUARD RATHER THAN A REPORT. What fired it was the reading itself: `pct99`, a 99th percentile over every rope-coloured pixel in the corridor, which cannot tell a cord from lamp-lit rock and pinned at 0.4624 and 0.4634 against rims of 0.4650 and 0.4656 -- saturated, and hard-FAILing on xvfb + software Vulkan every run. `_bow_now` now returns the per-station peak with the physical ceiling applied, divided by |cos(chord angle)| to undo the projection onto the chord, and BOTH renderers read 0.3631 against the renderer's own rope_sag of 0.3718 (97.7%). CI run 32566211211 on 32e7a45 took the display job from 15 PASS / 1 FAIL to 16 PASS / 0 FAIL with this row resolving ASSERTED. KEPT RATHER THAN DELETED: the saturation guard it routes from is still live and still correct, so a renderer that genuinely pins would still reach it -- what has gone is the condition that made it fire every run, not the condition it exists for. The earlier reading here, that it was misfiled and belonged as a VOID, was written while saturation looked like a property of the environment. It was a property of the estimator.

save-durability.failed-backup	check_save_durability	env	ANSWERED, AND IT WAS ANSWERED IN THE ACTIONS TAB THE WHOLE TIME. It fires when the platform lets copy_absolute write onto a directory, which is the forcing function for the whole failed-backup path -- the guard whose failure costs a person their data. It has never fired on macOS. I recorded it as the highest-stakes unmeasured row because check_save_durability is a plain `add` and CI runs it on Linux with different filesystem semantics. CI run 32448201825 on bd2b1d7 prints `[10/103] check_save_durability (P0) PASS 22s` -- a plain PASS, no asterisk, no skip count -- so Linux blocks the copy exactly as macOS does and the path IS exercised on both. Kept as a defensive env row rather than deleted, because the row now documents an answered question and the next platform is not free. Found by reading the CI log for the thing I had said I could not measure.
bindings.file-order-control	check_binding_persistence	env	MISLABELLED, AND KEPT HERE UNTIL SOMEBODY DECIDES WHAT IT SHOULD BE. Its condition is ConfigFile returning the same key order for both writes, which is DETERMINISTIC for a given engine build and key set, not environmental -- it will always fire or never fire on a given version, not sometimes. `env` is describing a coin that is actually a constant. Today it never fires and the precedence control works; one engine update and that control is permanently dead with nothing saying so. A review reading.
prose.wide-word-list	check_prose	env	The wide sweep's authorship word list is kept OUT of the repository, because a banned-word list naming the words a reader would look for publishes its author's expectation of finding them, and every word on it already occurs zero times in the tracked tree -- the only surviving instance of each was the line forbidding it. So the list ships separately (tools/prose_words.txt, held out through .git/info/exclude; SF_PROSE_WORDS overrides). The consequence is that a fresh clone and CI have the gate without the list, and this row is what stops that reading as a pass over words that were never tested. The narrow sweep is unaffected and still asserts on scenes/ and src/. AN OPEN QUESTION, and it is a real trade rather than an oversight: the protection now exists on the machines that do not need it and is absent where the tree becomes public. Shipping the list as salted digests would get both properties at once and is the better answer if the obfuscation is judged acceptable to a reader; that is a publication call, not a code one.
